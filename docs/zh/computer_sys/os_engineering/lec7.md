# Lec 7 页面错误



## 页面错误场景



### 虚拟内存

虚拟内存主要有两个好处

1. 一个是隔离，从某种意义上说，隔离是，虚拟内存允许操作系统，给每个应用程序提供自己的地址空间，使一个应用程序不可能意外地或恶意地修改另一应用程序的地址空间。它还提供了用户和内核地址空间之间的隔离
2. 虚拟内存的另一个好处，它提供了一定程度的间接性。处理器指令，只使用虚拟地址，内核控制着从虚拟地址空间到物理地址空间的映射

> 1.  跳板页(trampoline page)。允许内核将一个页面映射到多个地址空间
> 2. 是守护页（guard page)，它用来在用户空间和内核空间中保护栈。



xv6 对异常的响应相当简单：如果用户空间发生异常，内核会终止出错的进程；如果异常发生在内核中，内核会崩溃。然而，实际的操作系统往往会有更有趣的响应方式。下面介绍几个比较广泛利用页错误的场景。

### 示例：写时复制

例如，许多内核使用页错误来实现写时复制（Copy-on-Write，COW）的 `fork`。`fork` 会导致子进程的初始内存内容与 `fork` 时父进程的内存内容相同。xv6 通过 `uvmcopy`（`kernel/vm.c:301`）来实现 `fork`，它会为子进程分配物理内存，并将父进程的内存内容复制到子进程中。然而，如果子进程和父进程可以共享父进程的物理内存，效率将会更高。但这种简单的实现方式无法奏效，因为它会导致父进程和子进程由于共享堆栈和堆内存的写操作而干扰彼此的执行。

![image-20240913083952829](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/66e389f57aa38.png)

通过恰当使用**页表权限**和**页错误**，父进程和子进程可以安全地共享物理内存。当虚拟地址在页表中没有映射，或映射中 PTE_V （*Page Table Entry*  ）标志被清除，或者权限位（PTE_R, PTE_W, PTE_X, PTE_U，）禁止当前操作时，CPU 会引发页错误异常。RISC-V 区分三种页错误：加载页错误（当加载指令无法转换其虚拟地址时）、存储页错误（当存储指令无法转换其虚拟地址时）和指令页错误（当程序计数器中的地址无法转换时）。`scause` 寄存器指示页错误的类型，`stval` 寄存器包含无法转换的地址。

COW fork的基本思路是，父进程和子进程最初共享所有物理页面，但它们将页面映射为只读（即清除PTE_W标志）。父子进程都可以读取共享的物理内存。如果其中一个进程写入某个页面，RISC-V CPU会引发页错误异常。内核的trap处理程序会执行如下操作： 

1. 响应时会分配一个新的物理页面，
2. 复制原物理页的内容到新分配的页中。
3. 更改出错进程页表中的相关PTE，以指向副本，并允许读写操作
4. 然后在引发错误的指令处恢复执行。

由于PTE现在允许写入，重新执行的指令将不再导致错误。写时复制需要进行某些记录管理，以帮助决定何时可以释放物理页面，因为每个页面可能会被多个页表引用，这取决于fork、页错误、exec和exit的历史。这个记录管理允许一个重要的优化：如果某个进程遭遇存储页错误，而该物理页面只被该进程的页表引用，则不需要复制。

COW fork使得fork速度更快，因为fork不需要立即复制内存。稍后，某些内存可能需要在写入时复制，但通常大部分内存不需要复制。一个常见的例子是fork之后执行exec：在fork之后可能会写入少量页面，但随后子进程的exec系统调用，它会用一个新的可执行程序替换当前进程的内存空间，从而释放大部分从父进程继承的内存。COW fork进一步优化了， 消除了这种内存复制的需求。此外，COW fork是透明（transparent）的：应用程序无需进行任何修改即可从中受益。

### 需要的信息

在内核中，将页表和页面错误结合起来，可以实现VA到PA的动态映射。那内核需要响应这个页面错误，那么它需要什么信息才能做出回应？

- 错误的虚拟地址
  - 通过``stval``寄存器（”Store Trap Value“）
- 错误类型，我们可能希望做出不同的回应
  - 通过``scause``寄存器
  - 加载或保存指令引起，或者是 ecall 指令（R /  W / Interrupt)等等

- 引起页面错误的指令的虚拟地址
  - 通过``spec``寄存器（管理者模式异常程序计数器）， 作为Handler代码的一部分，它保存在trapframe->epc

#### Xv6的实现

xv6 提供的系统调用``sbrk``

- 它允许应用程序增加自己的堆空间，输入参数的数字是你想要分配的页数
  - 如果是负数则缩小其地址空间
- 当应用程序启动时， sbrk堆的底部，栈的顶端
  - 实际上，这也是 p->sz （p: struct proc, sz: Size of process memory） 指向的地方。
- 当调用 sbrk 系统调用时
  1. 内核分配物理内存，映射到用户程序的地址空间
  2. 将内存清0
  3. 从系统调用返回。
- sbrk 是急分配，区别与惰性分配，也就是说，只要一调用 sbrk ，内核会立即分配应用程序需要的物理内存。
- 在实践中，应用程序很难预测，它需要多少内存，所以，通常情况下，应用程序会多申请，所以，它们申请的比需要的多。通常，我们完全可以以一种聪明的方式做出回应，通过使用惰性分配（lazy allocation）。

#### 惰性/按需页面分配

基本思路：在 sbrk 只是记住增加了地址空间，但不实际地分配物理内存，然后，在某个时刻，应用程序可能会使用该内存， 即如果条件满足``stack < va < p->sz ``，这会导致页面错误。因为，我们没有映射那块内存到页面映射中。

在页面错误处理程序中，

1. 我们可以分配一个页面，使用 kalloc 
2. 置零
3. 映射到页表中，更新页表
4. 然后重启指令

> 惰性分配在什么情况下，应用程序才会知道没有物理内存？

从应用程序的角度看，有无限多的内存。当然在某些时候，你可能用得太多了，基本上使用了所有物理内存，所以，如果它再多申请一页，这个时候，物理内存不够用了。然后内核可以采取几个操作。这就引出了一个话题，我们有一组运行在操作系统上的进程，而物理内存是有限的，并且这些有限的物理内存必须以某种方式在应用程序之间共享。

现代操作系统采用惰性分配内存 计划： 当应用程序需要时才分配物理内存 在 `sbrk` 调用时调整 `p->sz`，但不实际分配内存 当应用程序使用这块内存时，会触发页面错误 在页面错误时分配内存 然后在出错的指令处继续执行 这样可能会使用更少的内存 如果没有使用内存，就不会触发页面错误，也就不会进行分配 将分配的开销分摊到页面错误发生时，而不是在 `sbrk()` 时一次性全部分配

#### 按需补0

一个几乎是微不足道的，但是经常使用的。事实上，在操作系统中，有很多空页

- 应用程序通常有很大一部分内存需要填充为零 比如全局数组等，位于 "block starting symbol" (BSS) 段
- 因此，内核经常需要将一个页面填充为零
- 思路：使用 `memset` 函数将 *一个* 页面填充为零 当内核需要零填充页面时，将该页面以写时复制（copy-on-write）的方式映射 当进行写操作时，复制该页面并将其以读/写方式映射到应用程序的地址空间

另一个广泛使用的利用页错误的功能是按需分页。在Xv6的原始版本的`exec`中，xv6会”急切“加载应用程序的所有文本和数据段到内存中。由于应用程序可能很大，而从磁盘读取的开销很高，这种启动成本对用户可能会有明显影响：当用户从shell启动一个大型应用程序时，可能需要很长时间才能看到响应。为提高响应速度，现代内核会为用户地址空间创建页表，但将这些页的PTE标记为无效。当发生页错误时，内核从磁盘读取页面内容，并将其映射到用户地址空间中。与COW fork和惰性分配类似，内核可以透明地实现此功能。
