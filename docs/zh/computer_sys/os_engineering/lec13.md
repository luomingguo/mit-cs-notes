## 文件系统

> 为什么需要文件系统？

Solution：

- 提供耐久性(durability)/持久性(persistence)
  - 重启后仍然可用

- 提供对文件命名和组织方式
- 支持程序和用户之间的共享文件 

> 文件系统有哪些挑战？ 或者说它为什么有趣

因为它涉及到多种技术：

- 必须支持崩溃恢复(Crash Recovery)
  - 发生崩溃时（比如电力故障）发生了， 再重启之后仍然能够正常工作。

- 能共享/并发访问文件
  - 不同的进程可能同时操作文件系统，因此文件系统代码必须进行协调，以维护不变量
- 磁盘布局
  - 文件系统需要在磁盘上有数据结构来表示命名的目录和文件树，记录每个文件内容所在块的身份，并记录磁盘上哪些区域是空闲的
- 支持缓存（为了性能加速）
  - 磁盘访问比内存要慢很多，因此需要维护对热点块的缓存


### 提供的API  

UNIX/Posix/Linux/xv6等等

```c
fd = open("x/y", -);
write(fd, "abc", 3);
link("x/y", "x/z"); // 让同个文件赋予多个名称
unlink("x/y"); // 删除
write(fd, "def", 3);
close(fd);
// 文件 z 中包含 abcdef
```

Python 提供了 IO 或者 OS 模块，是以这些API作封装的。

### 设计哲学

- 基本对象：文件（而不是虚拟磁盘，DB对象）
- 内容：字节数组（而不是固定的80比特的记录，B树等）
- 命名： 人类刻度（而不是对象ID）
- 组织：通过目录形成层次化的组织方式
- 同步：无显式同步机制（而不是通过锁或是版本控制）
  - 例如，`link()` 和 `unlink()` 可以在另一个进程执行 `open()` 时并发修改名称层次结构
    - `link()`：为文件创建一个新的硬链接，即为同一个文件（inode）添加一个新名字。
    - `unlink()`：删除一个文件的名字（链接），如果该名字是文件的最后一个链接，则删除文件本身。

很多其他文件系统，在设计上可能跟UNIX的有很大的不同。



### API的实现

- 在``open``时， 文件描述符（或者说句柄） ``fd``引用着某个文件，即便文件名更改或者是被（其他进程）删除，其内容的访问不会受到影响
- 一个文件可能会有多个``link``，即，它可以出现在多个目录中，这些链接中的任何一个都不是“特殊”的。因此，文件的相关信息必须存储在目录之外的其他地方。

基于上述特点，我们这样实现FS：

- FS在磁盘上通过inode记录文件信息
- 文件系统通过i-number(inode的编号， 文件描述符的内部表示)引用inode
- inode包含链接计数（link count)，用于决定何时释放文件
- 延迟释放的inode的机制确保，文件在有任何引用时不会被删除，防止未关闭的FD引用到已释放的数据块，造成数据损坏和安全问题。



## Xv6 文件系统

### 软件分层

从上到下的分别是：

- 系统调用层
- 命名操作 | FD 操作层
- inodes 层
  - 为每个文件提供了称为inode的表示形式（元数据），有一个唯一的i-number和文件内容所在块的信息等
- inode cache 层
  - inode也是保存在磁盘的，缓存inode，并且提供同步机制
- log 层
  - 为上层提供事务机制，将多个块的更新封装成事务，确保在即便发生crash下，相应块能够自动更新
- buffer cache 层
  - 缓存热点磁盘块，并且用同步机制访问，确保在同一时间只有一个内核进程可以修改特定块
- virtio_disk 驱动层
  - 本来是磁盘层，这里面用到了虚拟化I/O，作用是读写块

数据存储在非易失性介质上——在无电力情况下数据能够保持在磁盘上，常用的存储介质：

- HDD（hard disk drives）硬盘：空间大、不贵但是读写较慢
- SSD（solid state drives）固态硬盘： 空间较小，较贵但是读写速度快

历史上，磁盘的读写的以512B为单位，称为扇区。（这种与FAT32）有较好的兼容性。

HDD的特点：

- 同心轨道（concentric tracks）
- 每个轨道由一系列的扇区组成，是硬盘读写的基本单位
- 磁头需要移动到目标轨道，或者说寻道（seek），盘片必须旋转到目标扇区为止
  - 导致了随机访问比较慢（5 - 10ms 一次）
  - 顺序访问比较快（100MB/s）

SSD的特点：

- 基于非易失性“闪存”（flash memory）
- 随机访问：100ms
- 顺序访问：500MB/s
- 内部机制复杂 ——比如块重映射（remapping）、垃圾回收（garbage collection）、磨损均衡（wear leveling），虽然对外部用户隐藏，但是会在性能上体现出来
  - 闪存需要在写入数据前，先将原有数据块擦除
  - 每个闪存块的写入寿命是有限的（约数千次到数万次）
  - 因此，使用块重映射将逻辑地址映射到物理存储块上，从而实现磨损均衡

HDD和SSD的共同特点：

- 顺序访问比随机访问更快
- 大块读写比小块操作更加高效
- 上述这些都影响了FS的设计和性能

**磁盘块**（disk block）：为了局部性原理和摊销读写性能，减少记录的开销，大部分操作系统都会使用4KB（也就是8个扇区大小）为单位的读写单位。Xv6则是使用了2个扇区的块

### 磁盘布局

xv6将从磁盘读取的块保存在类型为`struct buf`（`kernel/buf.h:1`）的对象中，从文件系统的角度来看，磁盘是巨大的块数组（忽略了磁盘的物理属性）

![image-20240917161557347](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/66e93ad6723ea.png)

- 图8.2： 文件系统在磁盘的布局

梳理下布局

- 块 0 ，不使用，或者作为引导块
- 块1，超级块。它包含文件系统的元数据（文件系统的大小（以块为单位）、块的数量、inode的数量和日志块的数量）
  - 超级块是由一个名为`mkfs`的单独程序填充的，该程序用于构建初始文件系统

- 块2-31：记录事务的日志
- 块32-44： inode的数组，被封装成块
  - 一个块可以有多个inodes

- 块45： bitmap，跟踪哪些数据块正在使用
- 块46开始：数据块。要么是为文件或目录保存内容，要么在bitmap上被标记为空闲

xv6的`mkfs`程序为空文件系统生成此布局：

- **布局在文件系统的生命周期内是静态的**

>  按照上面的磁盘布局，``read inode 1``需要访问哪个地址？

Sol：32 + #inode * 64(aka, inode size) / 1024(block size) ▯

> [!NOTE]
>
> “元数据”: 就是除了文件内容以外的其他东西，比如超级块，i-node，bitmap，目录内容

### 块缓存层

上述所说，主要目的是两件事：

1. 缓存热点磁盘块，并且
2. 用同步机制访问，确保在同一时间只有一个内核进程可以修改特定块

这里面涉及几个接口

```c
bread(); 		// 为磁盘上某个数据块进行在内存上进行缓存
bwrite();  	// 将内存缓存写回到特定块
brelse(); 	// 当一个内核线程完成了对这个块的时候，需要进行释放
bget();			// 通过在以下过程中始终持有 bcache.lock 来确保这一不变量：从第一轮循环检查块是否已缓存开始，一直到第二轮循环声明块现在已被缓存（通过设置 dev、blockno 和 refcnt）；
```

另外，缓存大小是有限制的，可能你请求的块并不在缓存里面，所以需要驱逐策略，将不活跃的块驱逐，最常用的是LRU

#### 代码实现

buffer cache用双线链表的buffer表示，所有的访问通过链表的``bcache.head``进行，一个buffer有两个状态字段，``valid``表示是否包含磁盘块的副本，``disk``表示，第一个buffer是最近最常用的，而最后一个是最近最少用的。

``bget()``通过两次循环，对现有缓冲区的扫描，在最坏情况下必须处理整个链表，但如果先检查最近使用的缓冲区（从 **bcache.head** 开始，沿着 **next** 指针），当引用具有良好的局部性时，可以减少扫描时间。而选择要重用的缓冲区时，通过向后扫描（沿着 **prev** 指针）选取最近最少使用的缓冲区。

### inode 层

inode是独立于名称的文件信息。inode 有两个相关意思。

- 它可以是引用磁盘上的数据结构，其包含了一个文件的大小，和对应块号列表
- 也可以是引用内存上的inode，包含了磁盘上的inode的副本以及一些在内核中需要的额外信息。位于inode缓存层

这里我把他们简单称为磁盘inode 和 缓存层 inode



#### 磁盘inode

磁盘inode被打包成一个连续的区域，叫inode块，每个inode大小相同（64B），这样就很容易通过一个i-number直接索引出来。磁盘inode定义在kernel/fs.h的``struct dinode``

- type（空闲、文件、目录、设备）

- nlink（链接数）

- size（文件大小）

- addr [12 + 1]

  - 12个直接块

  - 1个间接块

    - 一个数据块是1KB，保存256个块编号(块编号大小为4个字节)

  - 问最大的文件大小是多少？

    256 * 1024 + 12 * 1024 = 268KB 

每个inode都有一个i-number，这样容易通过i-number找到inde。在磁盘上通过字节寻址：``32 * BSIZE + 64 * inum``

>  如何找到文件的字节8000？▯

Solution: 逻辑块7 = 8000 / BSIZE (=1024) ，地址数组中的第8个条目（从块0开始）



#### 缓存层 inode

内核持有一个inode的集合，叫``itable``，在kerel/file.h ``struct inode``是 磁盘inode ``struct dinode``的副本，内核只有在C指针引用到inode采用被存储到内存中，``ref``字段统计了C指针引用缓存inode的计数，如果这个数字降为0时，内核会从内存中释放掉这个inode``iget``，``iput``用于更改引用计数

### 目录层

目录类似文件，也有自己的inode， 但是用户无法直接写入操作。目录的内容是由目录项（dirent）数组组成。一个目录项包含内容如下

| inum#                                  | 文件名         |
| -------------------------------------- | -------------- |
| 2个字节，如果inum为0，dirent是空闲的， | 14字节的文件名 |

**你应该将FS视为在磁盘上的数据结构**，目录，inodes和数据块形成的树状结构，它有两种分配池：

- inode分配池
- 块分配池



### FD操作层

在Unix接口中大部分资源都表示为文件，实现这种统一性的正是FD操作层。

Xv6为每个进程提供了自己的打开文件表，即FD表，每个打开的文件由一个``struct file``表示，它是对inode或管道的封装，同时还包括一个I/O偏移量。如果多个进程独立打开同一个，则不同示例有不同的偏移量。管道没有偏移量，inode函数要求调用者负责加锁。inode加锁的一个副作用是，读取和写入偏移量是原子更新的，因此多个进程同时写入同一个文件不会覆盖彼此数据，尽管写入可能会交错。

### 系统调用层

有几个系统调用值得学习，同时也是学习使用事务的很好的例子。使用事务，简化了实现，因为它原本需要多次更新磁盘块，但是我们不需要担心其执行顺序，要么成功要么无任何变化。

``sys_link``，为存在的inode创建了新的命名，而``create``创建新的inode冰创建了新的命名。

### 示例：``echo hi > x``

右边部分的注释，是我们根据前面提到的磁盘的布局，我们可以推测出操作。

```shell
$ echo hi > x
// create
bwrite: block 33 by ialloc   // allocate inode in inode block 33
bwrite: block 33 by iupdate  // update inode (e.g., set nlink)
bwrite: block 46 by writei   // write directory entry, adding "x" by dirlink()
bwrite: block 32 by iupdate  // update directory inode, because inode may have changed
bwrite: block 33 by iupdate  // itrunc new inode (even though nothing changed)
// write
bwrite: block 45 by balloc   // allocate a block in bitmap block 45
bwrite: block 770 by bzero   // zero the allocated block (block 770)
bwrite: block 770 by writei  // write to it (hi)
bwrite: block 33 by iupdate  // update inode
// write
bwrite: block 770 by writei  // write to it (\n)
bwrite: block 33 by iupdate  // update inode
```

### 文件系统的并发

Xv6的质朴的目标：

- 在不同文件实现并行读写
- 并行的路径查找

比如，如果对``ialloc``有并发调用怎么办？ 他们会得到相同的inode吗？注意``ialloc``有``bread / bwrite / brelse``操作，``bread``会对数据块加锁，可能会waiting，从磁盘中读取数据，``brelse``会解锁这个数据块

### 数据块缓存

数据块缓存维护着最近使用的数据块``bcache``，FS调用``bread``，这个会调用``bget``，其作用是查找指定数据块是否被缓存，如果有的话，就将其加锁并返回这个缓存块，也有可能会通过睡眠锁等待，直到当前使用的进程释放后；如果不在，那么就会重用当前已经存在的buffer，``b->refcnt++``来阻止被回收当我们进行等待的时候。

不变量： 磁盘块在内存中最多只有一个副本

### 两级锁

- ``bcache.lock``保护在缓存中的描述符
- ``b->lock``保护一个缓冲区







#### 查找（lookup）路径名

将查找顺序倒序，潜在地会涉及到以下数据块：

- 顶部目录的inode
- 顶部目录的数据
- 逐层下降的inode

每个结构都可能导致cache miss，这样磁盘访问会非常昂贵。

并且需要支持平行的查找路径名。

一个进程可能阻塞在磁盘，另外一个可能在处理查找

一个挑战：unlink操作可能与lookup并发

#### 通过路径名称查找inode

根据路径名查找inode函数``struct inode* namex(path, nameiparent, name)``的实现（kernel/fs.c）：

- 入参：
  - path: 目录路径
  - nameiparent: 是否找目录
  - name：从path解析出来

- 调用``ilock()``，锁定当前目录
- 查找下个目录的inode
- 然后解锁当前目录，允许其他进程访问
- 如果另一个进程在查找过程或者你调用了``unlink``了第二步inode，但由于该inode的引用计数（refcnt）大于0，inode不会被删除
- 风险：查找的目录项可能与当前目录项相同（即查找"."目录)
  - 办法：在解锁当前目录之前，先获取下一个目录的锁。
  - 关键点: 引用计数与锁是分开的。






## 现在操作系统

现实世界的OS的缓存区缓存要比Xv6复杂的多，但是基本思想都是一样，缓存和同步对磁盘的访问。LRU的驱逐策略，运用比较广泛，一种更高效的 LRU 缓存可以通过消除链表来实现，具体来说，使用哈希表进行查找，并使用堆来管理 LRU（最近最少使用）的淘汰操作。

现代OS缓冲区缓存典型地通过与虚拟内存系统集成来支持内存映射文件（memory-mapped files)。`mmap` 和 `munmap` 系统调用允许 UNIX 程序对其地址空间进行详细控制。它们可以用于在进程之间共享内存、将文件映射到进程的地址空间中，以及作为用户级页面错误处理机制的一部分。

Xv6的日志系统是不高效的。在多个文件系统调用时不能实现并发提交。系统记录整个块的日志，即使一个块中只有少量字节发生了变化。它以同步的方式逐块写入日志，而每次写入可能都需要完整的磁盘旋转时间。真正的日志系统会解决所有这些问题。

Xv6对磁盘故障处理比较简单——磁盘操作失败就崩溃。如果操作系统运行在使用冗余来掩盖磁盘故障的特殊硬件之上,那么操作系统可能很少遇到故障,这种处理方式可能是可以接受的。另一方面,使用普通磁盘的操作系统应该预期会出现故障并更优雅地处理它们,这样一个文件中的块损坏就不会影响整个文件系统的使用。

Xv6要求文件系统必须适合一个磁盘设备且大小不能改变。随着大型数据库和多媒体的存储存储需求的增长，OS正在开发方法消除“每个文件系统一个磁盘的”的瓶颈。基本方法是，多个磁盘组合成一个逻辑磁盘。硬件解决方案如RAID仍然最受欢迎，当时当前趋势是尽可能地在软件中实现这种逻辑。这些软件实现通常允许丰富的功能，如通过动态添加或移除磁盘来增大或缩小逻辑设备，xv6使用的固定大小的inode块数组在这种环境下就不适用了。

Xv6缺少现代文件系统的特性，例如不支持快照和增量备份。

现代 Unix 系统允许使用与磁盘存储相同的系统调用来访问多种类型的资源:命名管道、网络连接、远程访问的网络文件系统以及监控和控制接口(如 /proc)。这些系统通常不像 xv6 在 fileread 和 filewrite 中使用 if 语句那样,而是为每个打开的文件提供一个函数指针表,每个操作对应一个指针,并通过调用函数指针来调用该 inode 对该调用的实现。网络文件系统和用户级文件系统提供的函数将这些调用转换为网络 RPC,并等待响应后再返回。
