## 调试技巧

- xv6 没有 `ps` 命令，但如果你按 `Ctrl-p`，内核会打印每个进程的信息。如果你现在尝试，你会看到两行输出：一行是 `init` 进程的信息，另一行是 `sh` 进程的信息。要退出 qemu，请按 `Ctrl-a x`

- 你可能会发现你的打印语句生成了大量输出，难以手动查找。可以尝试在 `script` 内运行 `make qemu`（在你的机器上运行 `man script` 以了解更多），这会将所有控制台输出记录到文件中，之后你可以搜索该文件。别忘了退出 `script`。

- Qemu有“监控器”能让你查询到状态，可以用过输入``control-a + c``（c表示"console")，一个特别有用的monitor命令是， ``info mem``，用于1打印页表，你可能需要用``cpu``命令来选择要看哪个核的``info mem``，或者你在开始qemu时用``make CPUS=1 qemu``来限制CPU数量
- 如果你想查看编译器为 xv6 内核生成的汇编代码，或者想知道某个特定内核地址对应的指令，可以查看文件 `kernel/kernel.asm`。这是在编译内核时由 Makefile 生成的。（Makefile 还会为所有用户程序生成 `.asm` 文件。）
- 如果你的内核卡住了，可能由于死锁导致。你可以用gdb来找到哪里发生了死锁。通过在一个窗口运行``make qemu-gdb``，在另外一个窗口运行gdb（比如``riscv64-linux-gnu-gdb``），然后按``c``继续，直到内核卡主了， 此时在``qemu-gdb``的窗口用``Ctrl-C``，然后输入``bt``查看调用栈
- 如果你的内核出现奇怪的错误（比如使用了不合法的地址），它会在crash的地方打印错误信息，包括PC("sepc")；你可以搜索``kernel.asm``来找到包含这个PC的函数，或者你可以运行``addr2line -e kernel/kernel [pc-value]``（可以通过``man addr2line``看看细节）。如果你想要调用栈，那就用上述的gdb方法，在此之前在在panic函数下断点，``b panic``，直到捕捉到时，用``bt``查看调用栈
- f you start gdb and see a warning of the form 'warning: File ".../.gdbinit" auto-loading has been declined', edit ~/.gdbinit to add "add-auto-load-safe-path...", as suggested by the warning.)

### Fork

- 一个进程创建一个进程用fork，得到相同的内存内容（指令和数据），在原进程，fork返回新进程的PID，对于新进程，返回0

- 父进程如果调用``wait``，其返回值会被存储到pid变量，而不会改变子进程的pid变量，而保持为0

- 子进程**从 `fork()` 调用的那一刻**开始执行，也就是从父进程调用 `fork()` 的地方继续执行

- 文件描述符和 `fork` 的交互使得 I/O 重定向的实现变得容易。`fork` 会复制父进程的文件描述符表和内存，因此子进程一开始就与父进程拥有完全相同的打开文件。`exec` 系统调用会替换调用进程的内存，但保留其文件表。

  - **新分配的文件描述符总是当前进程中未使用的最小编号**

  - ```c
    // cat < input.txt的简化代码版本
    
    char *argv[2];
    argv[0] = "cat";
    argv[1] = 0;
    if(fork() == 0) {
      close(0);
      open("input.txt", O_RDONLY);
      exec("cat", argv);
    }
    ```

  - 子进程关闭文件描述符 0 后，`open` 保证会使用该文件描述符来打开新文件 `input.txt`：0 将是最小的可用文件描述符。此时，`cat` 进程的文件描述符 0（标准输入）将指向 `input.txt`。父进程的文件描述符不会受到影响，因为该序列只修改了子进程的描述符。

### Exec

`exec` 系统调用会用文件系统中存储的文件加载的新内存映像替换调用进程的内存。该文件必须具有特定的格式，指定文件中的哪一部分包含指令，哪一部分是数据，程序从哪条指令开始执行等。Xv6 使用 ELF 格式。当 `exec` 成功时，它不会返回到调用程序；相反，文件中加载的指令会从 ELF 头部声明的入口点开始执行。`exec` 接受两个参数：包含可执行文件的文件名和一个字符串参数数组。例如：

```c
char *argv[3];
argv[0] = "echo";
argv[1] = "hello";
argv[2] = 0;
exec("/bin/echo", argv);
printf("exec error\n");
```

这一段代码将调用程序替换为运行 `/bin/echo` 程序的实例，并使用参数列表 `echo hello`。大多数程序会忽略参数数组的第一个元素，按照惯例，这个元素是程序的名称。

xv6 的 shell 使用上述调用来代表用户运行程序。shell 的主要结构非常简单；参见 `main` (user/sh.c:145)。主循环通过 `getcmd` 从用户那里读取一行输入。然后它调用 `fork`，创建 shell 进程的副本。父进程调用 `wait`，而子进程运行该命令。例如，如果用户在 shell 中输入了 "echo hello"，`runcmd` 会以 "echo hello" 作为参数被调用。`runcmd` (user/sh.c:58) 运行实际的命令。对于 "echo hello"，它将调用 `exec` (user/sh.c:78)。如果 `exec` 成功，子进程将执行 `echo` 中的指令，而不是 `runcmd`。在某个时刻，`echo` 将调用 `exit`，这会导致父进程从 `main` 中的 `wait` 返回 (user/sh.c:145)。

你可能会想，为什么不将 `fork` 和 `exec` 结合为一个调用？因为在这两者之间，shell 有机会在不干扰主 shell 的 I/O 设置的情况下重定向子进程的 I/O。 避免创建一个重复的进程然后立即用 `exec` 替换掉它的浪费，操作系统内核通过使用虚拟内存技术（如写时复制，参见第4.6节）来优化 `fork` 的实现以应对这种情况。

xv6 大多数用户空间的内存分配是隐式的：`fork` 为子进程分配父进程内存的副本所需的内存，而 `exec` 则为可执行文件分配足够的内存。一个在运行时需要更多内存的进程（例如为了 `malloc`）可以调用 `sbrk(n)` 来将数据内存扩展 n 字节；`sbrk` 返回新内存的位置

### dup

`dup` 系统调用会复制一个现有的文件描述符，返回一个新的文件描述符，该文件描述符引用相同的底层 I/O 对象。这两个文件描述符共享一个偏移量，类似于 `fork` 复制的文件描述符。这是另一种将 "hello world" 写入文件的方法：

```c
fd = dup(1);
write(1, "hello ", 6);
write(fd, "world\n", 6);
```

如果两个文件描述符是通过 `fork` 和 `dup` 调用序列从同一个原始文件描述符派生出来的，那么它们共享偏移量。否则，即使它们是通过对同一个文件的 `open` 调用创建的，它们的偏移量也不会共享。`dup` 允许 shell 实现这样的命令

```bash
ls existing-file non-existing-file > tmp1 2>&1
```

命令中的 `2>&1` 告诉 shell 给命令分配一个文件描述符 2，它是文件描述符 1 的副本。这样，现有文件的名称和不存在文件的错误消息都会出现在文件 `tmp1` 中。虽然 xv6 的 shell 不支持对错误文件描述符的 I/O 重定向，但现在你知道如何实现它了。

文件描述符是一种强大的抽象，因为它们隐藏了它们实际连接到的内容细节：一个进程向文件描述符 1 写数据，可能是在写入一个文件、一个设备（比如控制台），或者一个管道。

### pipe

管道是一个由内核提供的小型缓冲区，通过进程的**一对**文件描述符来访问，一个用于读取，另一个用于写入。将数据写入管道的一端会使得这些数据可从管道的另一端读取。管道提供了一种进程间通信的方式

```c
int p[2];
char *argv[2];
argv[0] = "wc";
argv[1] = 0;
pipe(p);
if(fork() == 0) {
    close(0);
    dup(p[0]);
    close(p[0]);
    close(p[1]);
    exec("/bin/wc", argv);
} else {
    close(p[0]);
    write(p[1], "hello world\n", 12);
    close(p[1]);
}
```

该程序是想 **将父进程的输出作为子进程的输入并在子进程中执行 `wc` 命令**。 程序首先调用 `pipe`，创建一个新管道，`p[0]` 是读取端（读描述符），`p[1]` 是写入端（写文件描述符）。复制管道的读取端 `p[0]`，并将其分配到文件描述符 0，即标准输入。这意味着子进程接下来的标准输入将从管道中读取数据，而不是从键盘或其他输入设备。然后关闭管道的读取和写入端，因为它们已经不再需要在子进程中使用。最后子进程执行``wc``这时已经被重定向到管道的读取端。

在父进程中，管道的读取端 `p[0]` 被关闭，因为父进程不需要读取数据。然后，父进程使用 `write` 向管道的写入端 `p[1]` 写入字符串 `"hello world\n"`。这段数据会被写入到管道，传输给子进程。

如果管道中没有可用的数据，`read` 操作会阻塞，等待数据被写入，或者所有引用管道写入端的文件描述符都被关闭；在这种情况下，`read` 会返回 0，就像达到了文件末尾一样。`read` 阻塞直到确认不会有新数据到来，这也是为什么子进程在执行 `wc` 之前必须关闭管道的写入端：如果 `wc` 的某个文件描述符仍然指向管道的写入端，那么 `wc` 永远不会看到文件结束信号（EOF）。

xv6 的 shell 以类似的方式实现了管道，

xv6 的 shell 以类似的方式实现了管道，例如 `grep fork sh.c | wc -l`（参见 `user/sh.c:100`）。子进程创建一个管道来连接"|"的左端和右端。然后它调用 `fork` 和 `runcmd` 来执行管道的左端，再调用 `fork` 和 `runcmd` 来执行右端，并等待两端完成。管道的右端可能是一个包含管道的命令（例如 `a | b | c`），这会创建两个新的子进程（一个用于 `b`，一个用于 `c`）。因此，shell 可能会创建一个进程树。**树的叶子节点是命令，内部节点是那些等待左、右子进程完成的进程**。

假设我们修改 `sh.c`，使其不对 `p->left` 调用 `fork`，而直接在内部进程中运行 `runcmd(p->left)`，会出现以下问题：

1. **`echo hi | wc` 不会产生输出**：如果内部进程直接运行 `runcmd(p->left)`，那么当 `echo hi` 执行完毕后，内部进程也会退出，导致 `wc` 不会被执行。因为内部进程退出后，它不会继续执行管道的右端命令 `wc`
2. 在这种情况下，`echo hi` 会立即运行并退出，而不等待 `sleep 10` 完成。这是因为内部进程没有正确地处理管道的右端命令，导致 `echo` 立即执行，忽略了 `sleep` 的延迟

管道的行为和临时文件的行为有一些相似之处：

- **管道**：管道在内存中创建一个缓冲区，用于在两个进程间传输数据。它是临时的，并且在数据传输完成后会自动关闭。
- **临时文件**：临时文件则在磁盘上创建一个实际的文件，数据可以从一个进程写入，然后从另一个进程读取。使用临时文件进行管道处理的方式类似于在文件系统中创建一个中间文件来保存数据，然后通过重定向操作来传输数据。
