在考虑设计一个操作系统时，我们需要知道其需求有什么？这里整理了几个关键需求：

1. **多路复用**（多个程序并发运行），比如，启动一个编译器和一个文本编辑器，它们作为独立的两个进程运行
2.  保证进程之间的**隔离**，如果某个进程有 bug 或发生异常，不应该影响到无关的进程。但是
3. 又不能完全隔离，进程有时候需要有意地进行交互，例如管道。 简洁地说，**交互性**。

在介绍方案前，先回答为什么需要操作系统？ 一种替代方案是将系统调用（比如，`read`）实现成一个库，应用程序直接链接这个库，甚至可以有自己定制的版本。这种设计下，应用程序可以直接操作硬件资源，并且可以按自己的需求最优使用资源。这种设计在某些场景确实存在，比如嵌入式/实时系统。缺点是， 👉 如果有多个应用同时运行，所有应用必须“非常自觉”，这种方式叫 **协作式时间共享（cooperative time-sharing）**。



## 抽象物理资源

如何实现隔离性？

一个关键思路是，禁止应用直接访问敏感硬件资源，而是提供抽象服务。例如，在Unix中，应用不会直接操作磁盘，而是通过`open`、`read`、`close`等；CPU调度上，Unix会自动在进程之间切换CPU，并且保存/恢复寄存器状态，结果是应用完全感知不到时间共享；在内存管理上，Unix进程使用`exec`来构建自己的内存空间，而不是直接操作物理内存，由OS 决定进程放在哪里，内存不够时可以换出到磁盘（虚拟内存）；很多进程间交互通过 文件描述符 完成，隐藏实现细节（例如 pipe 数据存在哪里）。  系统调用接口被精心设计，同时满足 编程方便 和强隔离性的要求。







为了实现强隔离，操作系统必须确保，应用程序不能修改（甚至不能读取）操作系统的数据结构和指令；应用程序不能访问其他进程的内存。CPU提供了硬件支持来实现这种强隔离，例如，RISC-V 提供了三种特权级别，用来限制代码的行为：

- 机器态（machine mode）
- 管理态（supervisor mode）
- 用户态（user mode）

在机器态下执行的指令拥有最高权限；CPU 启动时处于机器态。机器态主要用于系统启动时的初始化工作。xv6 只在机器态下短暂运行，然后切换到管理态。在管理态下，CPU 可以执行特权指令，例如，开启或关闭中断；读写保存页表地址的寄存器。如果用户态中的应用程序尝试执行特权指令，CPU 不会执行该指令，而是会“陷入”（trap）到运行在管理态的特殊代码，由该代码决定终止这个应用程序。

应用程序通过系统调用（例如 `read`）与内核交互。应用程序不能直接调用内核函数，也不能直接访问内核内存。RISC-V 提供了 `ecall` 指令用于系统调用；该指令会将 CPU 从用户态切换到管理态，并跳转到内核指定的入口点。

当 CPU 切换到管理态之后，内核可以验证系统调用的参数（例如检查传入的地址是否属于应用程序的内存空间）；判断应用程序是否有权限执行该操作（例如是否允许写入指定文件）决定拒绝或执行该操作。



## 内核组织

一个关键的设计问题是：操作系统的哪些部分应该运行在管理态中。一种可能的设计是：整个操作系统都驻留在内核中，也就是说所有系统调用的实现都运行在管理态。这种组织方式称为**单体内核（monolithic kernel）**。

在单体内核结构中，整个操作系统就是一个运行在管理态下的单一程序。这种方式的一个优点是实现起来比较方便，因为操作系统设计者不需要将代码划分为“需要特权”和“不需要特权”的部分。此外，由于所有模块都在同一个程序中，不同部分之间的协作也很容易。例如，单体内核可以让文件系统和虚拟内存系统共享一个磁盘块缓存。

但缺点是：单体内核往往会变得庞大而复杂，导致没有任何一个开发者能够完全理解各个模块之间的交互关系，这很容易引入 bug。而内核中的 bug 尤其严重。

------

**微内核（microkernel）**的目标是减少内核中 bug 的发生概率。其核心思想是：只在内核中保留最少的功能，使得运行在管理态的代码尽可能少，从而让内核更容易理解和验证其正确性。

操作系统的大部分功能被移到用户态，以“服务器进程”的形式运行。例如，文件系统代码可以作为一个用户态服务器运行，而不是在管理态中执行。

![image-20260404133936927](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/image-20260404133936927.png)

图 2.1 展示了这种微内核设计。在图中，文件系统作为用户级服务器运行。为了让应用程序能够与文件服务器交互，内核提供了一种进程间通信（IPC）机制，允许用户态进程之间发送消息。例如，如果像 shell 这样的应用程序需要读写文件，它会向文件服务器发送消息，并等待响应。

在微内核中，内核接口只包含少量底层功能，例如：

- 启动应用程序
- 发送消息（IPC）
- 访问设备硬件

这种组织方式使得内核本身相对简单，因为操作系统的大部分功能都运行在用户态服务器中。



在现实世界中，单体内核和微内核都被广泛使用。

许多 Unix 系统采用单体内核。例如，Linux 使用的是单体内核（尽管某些操作系统功能运行在用户态，例如窗口系统）。Linux 在操作系统密集型应用中能提供很高的性能，部分原因是其内核子系统之间可以紧密集成。

而像 Minix、L4 和 QNX 这样的系统采用微内核结构，并在嵌入式场景中得到广泛应用。L4 的一个变种 seL4 规模足够小，已经被形式化验证，证明其在内存安全和其他安全属性方面是正确的。

## 进程

在 xv6（以及其他 Unix 操作系统）中，隔离的基本单位是“进程”。进程这一抽象可以防止一个进程破坏或窥探另一个进程的内存、CPU、文件描述符等资源。同时，它也防止进程破坏内核本身，从而避免进程绕过内核的隔离机制。





为了帮助实现隔离，进程这一抽象为程序提供了一种“拥有独立机器”的假象。一个进程为程序提供，看起来是“私有的内存系统”（即地址空间），其他进程无法读取或写入；看起来是“专属的 CPU”，用于执行该程序的指令。

xv6 使用页表（由硬件实现）为每个进程提供独立的地址空间。在 RISC-V 架构中，页表的作用是将虚拟地址（程序中使用的地址） 映射为物理地址（CPU 发送到内存的地址）



xv6 为每个进程维护一个独立的页表，用来定义该进程的地址空间。如图 2.3 所示，一个地址空间包含：从虚拟地址 0 开始的用户内存

布局顺序为：

1. 指令（代码段）
2. 全局变量（数据段）
3. 栈（stack）
4. 堆（heap，用于 malloc，可动态增长）

![image-20260404213511550](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/image-20260404213511550.png)

在地址空间的最顶部，xv6 放置了两个特殊页面（每个 4096 字节）

- trampoline page（跳板页）：包含进入/退出内核的代码
- trapframe page（陷阱帧页）用于保存用户寄存器状态，后面会讲



xv6 内核为每个进程维护了大量状态，这些状态被组织在一个 `struct proc` 结构体中（定义在 kernel/proc.h）。

进程最重要的内核状态包括：

- 页表（page table）
- 内核栈（kernel stack）
- 运行状态（run state）

我们用 `p->xxx` 表示 proc 结构体中的字段。例如，`p->pagetable`：指向该进程页表的指针



每个进程都有一个“控制线程”（thread of control），简称线程，用于保存执行进程所需的状态。在任意时刻，一个线程可能正在 CPU 上执行或处于挂起状态（暂不执行，但可以恢复）

当 CPU 在不同进程之间切换时，内核会暂停当前线程，保存它的状态，恢复另一个进程之前保存的线程状态，线程的大部分状态（例如局部变量、函数返回地址）都保存在栈中。每个进程有两个栈——用户栈（user stack）和 内核栈（kernel stack，p->kstack）

执行规则如下，在用户态执行时，使用用户栈，内核栈是空的。进入内核时（系统调用或中断），使用内核栈执行内核代码，用户栈仍保存数据，但不使用。线程会在这两个栈之间来回切换。



> 为什么需要单独的内核栈？

因为这样即使用户程序破坏了自己的用户栈，内核仍然可以安全执行。



用户程序可以通过执行 RISC-V 的 `ecall` 指令发起系统调用`ecall`会切换到 supervisor mode（内核态），跳转到内核入口地址。内核入口代码，切换到该进程的内核栈，执行系统调用逻辑；系统调用结束后，内核执行 `sret`，切回用户态，从 ecall 之后的指令继续执行。线程在内核中可能会“阻塞”，例如等待 I/O，I/O 未完成 → 线程暂停；I/O 完成 → 线程恢复执行。

`p->state` 表示进程的状态，例如：

- 已分配（allocated）
- 可运行（ready）
- 正在运行（running）
- 等待 I/O（sleeping）
- 即将退出（exiting）



`p->pagetable` 保存该进程的页表（符合 RISC-V 硬件格式）。当进程在用户态运行时，xv6 会让硬件使用该页表。页表同时也记录了，该进程所使用的物理内存页。



## 安全模型

你可能会想，操作系统是如何应对有 bug 或恶意的代码的。

由于应对“恶意行为”比处理“无意的错误”更困难，因此操作系统设计通常主要关注如何抵御恶意代码。下面是操作系统安全设计中一些典型的假设与目标的高层概述。操作系统必须假设：用户态进程中的代码会尽最大努力去破坏内核或其他进程。

例如，用户代码可能会尝试：

- 解引用（访问）其地址空间之外的指针
- 执行不允许在用户态执行的指令
- 读取或写入 RISC-V 的控制寄存器
- 访问设备硬件
- 向系统调用传入精心构造的参数，试图诱导内核崩溃或做出错误行为



内核的目标是限制每个用户进程，使其只能：

- 访问自己的用户内存
- 使用 32 个 RISC-V 通用寄存器
- 仅通过“系统调用允许的方式”影响内核和其他进程

内核必须禁止所有其他行为。这些通常是操作系统设计中的“绝对要求”。



对于内核自身代码的假设是不同的。我们通常认为，内核代码是由善意且谨慎的程序员编写的；内核代码没有 bug；内核代码不包含恶意逻辑。这个假设会影响我们分析内核的方式。



但现实情况并没有这么简单。

很难阻止恶意用户程序通过系统调用来消耗系统资源，从而使系统不可用，例如，占满磁盘空间；占用大量 CPU 时间；用尽进程表槽位。同时，几乎不可能写出 100% 无 bug 的内核代码，也不可能设计出完全无 bug 的硬件。如果恶意程序知道这些漏洞，它们就会加以利用。即使是成熟且广泛使用的内核（例如 Linux），也经常会发现新的安全漏洞。

## Xv6

### 概述

Xv6 运行在RISC-V 的CPU上， 需要特定的硬件设备叫 "SiFive HiFive Unleashed" 板，配置如下：

- RISC-V 处理器，4 个核心
  - 每个核心有 32 个寄存器、ALU、MMU、控制寄存器、计时器、总线接口等，核心之间共享 RAM 和设备。
  - 共享RAM、和板上设备
- 128MB RAM
- UART 用于控制台
- 磁盘式存储
- 以太网

Qemu 模拟该 CPU 和类似的硬件设备（如使用 `qemu -machine virt` 模拟 "virt" 板），https://github.com/riscv/riscv-qemu/wiki，非常接近Sifive开发板，但是磁盘用的是virtio

xv6 内核代码结构简单，比如文件系统位于 `kernel/fs.c` 中。在kernei/defs.h可以看到所有的模块和内部接口。可以通过 `make` 来构建整个内核，生成内核二进制文件和磁盘镜像（`fs.img`）。

### Qemu作用

- 使用 Qemu 模拟器将内核二进制文件加载到"内存中"，用``fs.img``模拟磁盘，
- Qemu 会将内核的第一条指令加载到模拟的内存中。
- Qemu 维护仿硬件寄存器、RAM和中断指令

   ```
   (gdb) b *0x80000000
   (gdb) c
   ```

2. 此时内核实在机器模式下（M模式），第一条指令会跳转到 `entry.S` 中定义的 `_entry` 标签。这个标签下的指令，设置栈并跳转到 C 代码中的 `start()` 函数。

4. ``main()``函数里面，core 0设置了软件其他核则是等待

#### 内存初始化

内核的内存分配器在启动时会通过 `kinit()` 和 `freerange()` 找到所有的物理内存页并将它们加入到一个链表中，每个内存页以 4096 字节的单位进行分配。

```
(gdb) b userinit
(gdb) c

```



#### 进程启动

启动第一个用户级程序 `init`（``user/init.c``），该程序会启动所有其他进程（比如 xv6 中的控制台 shell）。通过 `allocproc()` 函数为进程分配内存、创建页表，并设置进程的状态为可运行 

#### 系统调用的执行：

进程通过系统调用（如 `exec()`）来启动其他程序。`ecall` 指令触发系统调用，内核通过读取用户寄存器中的值（如 `a7`）来判断调用的具体系统调用号，并跳转到对应的内核处理函数中。

```
(gdb) b *0x0
(gdb) c
(gdb) tui disable
(gdb) x/10i 0

what's the effect of ecall?
(gdb) b syscall
(gdb) c
back in the kernel
(gdb) tui enable
(gdb) n
(gdb) n
(gdb) n
(gdb) print num
      from saved user register a7
(gdb) print syscalls[7]
(gdb) b exec
(gdb) c 
```



#### ELF 格式的执行：

`exec()` 系统调用会从磁盘读取 ELF 格式的可执行文件，并将代码和数据加载到用户空间的内存中，同时为进程分配堆栈并设置入口点（epc，即程序计数器）和新栈起始指针（sp）
