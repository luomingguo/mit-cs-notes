### 1.1 论文解读

#### 1.1.1 正确性

我们首先定义什么是“正确”，即使对于看似简单的系统，明确定义系统应该如何行为是一个复杂的过程。以一个简单的键值存储为例进行说明，类似于etcd，该存储将字符串映射到字符串，并支持两种操作：Put(key, value)和Get(key)

当存在并发的 `Put("x", "y")` 和 `Put("x", "z")` 操作时，很难确定 `Get("x")` 操作应该返回什么值

我们使用称为线性一致性模型，根据顺序规范来规定并发操作的正确性。在线性一致性系统中，每个操作都表现为在调用和响应之间某个时刻原子性和即时地执行。虽然还有其他的一致性模型，但许多分布式系统提供了线性一致性的行为，因为线性一致性是一种强一致性模型，因此相对容易在其基础上构建其他系统

通用的方法就是随机注入错误，比如机器故障和网络分区。我们甚至可以模拟整个网络，因此可以做一些比如较大 的网络延迟等动作，因为检测是随机化的，我们需要运行足够的时间来保证系统实现是正确的

##### Ad-hoc 检测

那我们如果检测正确的操作呢？ 最简单的例子就是用形如assert(expect_output ==  f(input))的输入输出方法，我们将其应用到分布式系统，比如KV存储，我们可以用一下检测方法，该方法可以判断多客户端在KV存储中并行执行正确性

```go
for client_id = 0..10 {
    spawn thread {
        for i = 0..1000 {
            value = rand()
            kvstore.put(client_id, value)
            assert(kvstore.get(client_id) == value)
        }
    }
}
wait for threads
```

##### 线性一致性

更好的测试是让并行客户端运行完全随机的操作：例如重复执行`kvstore.put(rand(), rand())` and `kvstore.get(rand())`，也许只能使用一组小的键增加数据竞争。但在这种情况下，我们如何确定什么是“正确”的操作呢？由于客户端同时访问相同的键，因此无法为每个操作确定单一的预期输出。为了解决这一挑战，该段建议采用替代方法。与其关注预测单个操作的结果，不如记录系统上执行的所有操作历史，从而判断操作历史是否满足顺序规范

###### 线性化检查

该方法涉及使用线性化检查器，它接受两个输入：

- **顺序规范**：定义了系统在操作按顺序执行时的预期行为。
- **并发历史**：这是记录了多个客户端同时执行的操作历史。

###### NP-难问题

![截屏2024-04-15 16.35.21](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/661ce6dc0cd92.png)

线性化检查是NP完全问题的证明。让我们逐步解释：

1. **线性化检查是NP问题**：首先，作者指出线性化检查属于NP问题。这是因为，给定一个线性化（即所有操作的线性化点），我们可以在多项式时间内验证它是否符合顺序规范。因此，线性化检查可以在多项式时间内验证一个解是否正确。
2. **线性化检查是NP难问题**：作者接着证明了线性化检查是NP难问题。他们通过将一个已知的NP难问题——子集和问题（subset sum problem）——约化到线性化检查来实现。回顾一下子集和问题，给定一个非负整数集合S和一个目标值t，我们需要确定是否存在S的一个子集其和等于t。作者通过将子集和问题转换为线性化检查的问题来展示线性化检查的NP难性。
3. **转换子集和问题为线性化检查问题**：作者构造了一个顺序规范类Adder，其中包含了一个add方法用于将值添加到总和中，以及一个get方法用于获取当前总和。通过将子集和问题的实例转换为Adder类的一系列add操作和get操作，作者将子集和问题转换为了线性化检查问题。

4. **线性化历史与子集和问题的关联**：作者指出，给定一个线性化历史，如果该历史是线性化的，那么子集和问题的答案必定是“是”（存在一组元素的和等于目标值t）。反之亦然，如果子集和问题有解，那么可以构造一个线性化历史。**线性化历史的构造**：如果线性化历史存在，我们可以找到所有Add(s_i)操作，它们的线性化点在Get()操作之前。这些操作对应于一个子集，其元素的和等于目标值t。这是因为，在线性化历史中，这些Add(s_i)操作在Get()操作之前执行，因此它们的值将被包含在计算总和的过程中。**构造线性化**：如果子集和问题有解，我们可以构造一个线性化历史。具体地，我们将与子集中的元素相对应的Add(s_i)操作放置在Get()操作之前，而将其余操作放置在Get()操作之后。这样就构成了一个有效的线性化历史，其中Get()操作返回了正确的总和

###### 实现

尽管线性化检查是NP完全问题，但在实践中，对于小型历史记录，它仍然可以表现得相当好。线性化检查器的实现会接受一个可执行的规范和一个历史记录，并运行一个搜索过程来尝试构建一个线性化，使用技巧来限制搜索空间的大小。

已经存在一些线性化检查器，如Knossos，它在Jepsen测试系统中使用。然而，当我尝试测试我写的分布式键值存储的实现时，我无法让Knossos检查我的历史记录。Knossos在一些并发客户端的历史记录上似乎运行得不错，大约有一百个历史事件，但在我的测试中，我有数十个客户端生成数千个事件的历史记录。

为了能够测试我的键值存储，我编写了Porcupine，一个用Go实现的快速线性化检查器。Porcupine检查历史记录是否相对于用Go编写的可执行规范是线性化的。从经验上看，Porcupine比Knossos快数千倍。我能够使用它来测试我的键值存储，因为它能够在几秒钟内检查数千个事件的历史记录

### 1.2 FQA

**Q: 什么是线性一致/可线性化？**

A: 线性一致性是定义服务在处理并发客户端请求时应该表现的正确性的一种方式。简单来说，它指定服务应该看起来就像在请求到达时依次执行每个请求。  

线性一致性是基于“历史”来定义的：实际客户端请求和服务器响应的轨迹，由客户端发送和接收每个消息的时间加以注释。线性一致性告诉你一个个体历史是否合法；我们可以说一个服务是线性一致的。如果每个历史都是可线性化的。  

对于每个客户请求，请求消息发送到服务器和相应消息都是历史中的单独元素，每个消息在客户端发送或接收时出现。 因此，历史记录使请求并发和网络延迟变得明确。

如果可以为每个操作分配一个“线性化点”（时间），则历史记录是可线性化的，其中每个操作的点位于客户端发送请求和接收响应的时间之间，并且历史记录的响应值与按点顺序一次执行一个请求时获得的值相同。如果没有线性化点的赋值满足这两个要求，则历史记录不可线性化。 

线性化的一个重要结果是，服务在执行并发（时间重叠）操作的顺序上具有自由度。特别是，如果来自客户端 C1 和 C2 的请求是并发的，即使 C1 在 C2 之前发送请求消息，服务器也可以先执行 C2 的请求。另一方面，如果 C1 在 C2 发送请求之前收到响应，则线性化要求服务在 C2 之前执行 C1 的请求（即 C2 的操作需要观察 C1 操作的影响（如果有）

**Q: 线性一致性检查器如何工作**

该检查器会尝试每一种可能的顺序（或线性化点的选择），以查看是否有一种顺序符合线性一致性的定义规则。由于在大型历史记录上这样做会非常慢，聪明的检查器避免查看明显不可能的顺序（例如，如果一个提议的线性化点在操作的开始时间之前），将历史记录分解为可以单独检查的子历史记录，当可能时，使用启发式方法优先尝试更有可能的顺序。

**Q: 那么，服务是如何实现线性一致性的呢？**

如果服务是作为单个服务器实现的，没有复制、缓存或内部并行处理，那么服务几乎可以按照它们到达的顺序逐个执行客户端请求。主要的复杂性来自于客户端因为认为网络丢失了消息而重新发送请求：对于具有副作用的请求，服务必须小心确保不要执行同一个客户端请求超过一次。如果服务涉及复制或缓存，则需要更复杂的设计。

**Q: 如果两个命令同时执行，是否有可能强制执行特定的行为，使其中一个命令始终优先执行（即它始终具有较早的线性化点）？**

A:在一个线性一致性的存储服务（例如 GFS，或者你的实验三）中，如果来自多个客户端的请求几乎同时到达，服务可以选择执行它们的顺序。尽管在实践中，大多数服务会按照请求数据包到达网络的顺序执行并发请求。

线性化点的概念是用于检查历史是否是线性一致的一种策略的一部分。实际的实现通常不涉及显式的线性化点概念。相反，它们通常只是按照某种序列（一次一个）的顺序执行传入的请求。你可以将每个操作的线性化点视为服务执行请求的时间段中的某个时间点

**Q： 还有什么一致性模型**

- 最终一致性（eventual consistency）
- 因果一致性（causal consistency）
- 分叉一致性（fork consistency）
- 可串行化性（serializability）
- 顺序一致性（sequential consistency）
- 时间线一致性（timeline consistency）

此外，还有来自数据库、CPU 内存/缓存系统和文件系统领域的其他模型。

总的来说，不同的模型在应用程序员的直觉性和性能方面有所不同。例如，最终一致性允许出现许多异常结果（例如，即使写操作已经完成，随后的读操作可能看不到它），但在分布式/复制设置中，可以以比线性一致性更高的性能实现它

**Q： 为什么线性一致性被认为是一种强一致性**

A：这段内容强调了线性一致性的强大之处在于禁止了许多可能令应用程序员感到惊讶的情况。

举例来说，如果我调用了 put(x, 22)，并且我的 put 操作完成了，而且没有其他人写入了 x，随后你调用 get(x)，你将会保证看到的值除了 22 之外没有其他值。换句话说，读操作看到的是新鲜的数据。

另一个例子，如果没有人写入 x，而我调用了 get(x)，而你也调用了 get(x)，我们不会看到不同的值。

这些特性在一些其他的一致性模型中并不成立，比如最终一致性和因果一致性。这些后者的模型通常被称为“弱一致性”。

**Q：为什么要使用线性一致性作为一致性模型，而不是其他的模型，比如最终一致性？**

人们确实经常构建提供比线性一致性更弱一致性的存储系统，比如最终一致性和因果一致性。

线性一致性对应用程序编写者有一些好处：

- 读操作总是观察到新鲜的数据。
- 如果没有并发写入，所有读者看到的数据都是相同的。
- 在大多数线性一致性系统上，你可以添加类似于测试与设置的小型事务（因为大多数线性一致性设计最终都会一次对每个数据项执行操作）。

而像最终一致性和因果一致性这样的弱一致性方案可能会提供更高的性能，因为它们不要求立即更新所有数据的副本。这种更高的性能通常是决定因素。然而，弱一致性对于应用程序编写者引入了一些复杂性：

- 读操作可能观察到过时的数据。
- 读操作可能按顺序观察到写入操作。
- 如果写入后立即读取，你可能看不到自己的写入，而是看到过时的数据。
- 对同一项的并发更新不是逐一执行的，因此很难实现诸如测试与设置之类的小型事务。

**Q：为什么不使用客户端发送命令的时间作为线性化点呢？也就是说，让系统按照客户端发送的顺序执行操作？**

A: 确保这种行为是很困难的——开始时间是客户端代码发出请求的时间，但由于网络延迟，服务可能直到很久以后才收到请求。也就是说，请求可能以与开始时间顺序相差很大的顺序到达服务端。原则上，服务端可以延迟执行每个到达的请求，以防止稍后到达的请求比较早发出，但由于网络无法保证延迟，很难做到这一点。而且这会增加每个请求的延迟，可能会大大增加延迟。尽管如此，Spanner，使用了一种相关的技术。

像线性化这样的正确性规范需要在效率和为应用程序提供有用保证之间取得平衡。"按照调用顺序执行操作"的规范对于实现来说太严格，而线性化规范中的"似乎在调用和响应之间执行"是可实现的，尽管对应用程序员来说不太直观



**Q: 当并发执行多get()和一个put()而get到不同值，这种情况是正常的吗？**

A：在存储系统的上下文中，这通常不是问题。例如，如果我们谈论的值是我的个人资料照片，并且两个不同的人要求在我更新照片的同时查看它，那么他们看到不同的照片（旧照片或新照片）是很合理的。 一些存储系统提供了更复杂的方案，特别是事务，这使得这更容易。事务会自动锁定数据以防止并发读/写。“序列化性”是提供事务的一个一致性模型的名称。然而，事务系统比线性化系统更复杂、更慢、更难容错。
