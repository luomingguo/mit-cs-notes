## 总览

Boki 是一种新的无服务器运行时环境，向无服务器函数提供了共享日志 API。Boki 共享日志使有状态的无服务器应用能够以持久性、一致性和容错性管理其状态。Boki 共享日志实现了高吞吐量和低延迟。关键的推动因素是 metalog，这是一种新颖的机制，允许 Boki 分别处理排序、一致性和容错性。Metalog 使用高吞吐量对共享日志记录进行排序，并提供读取一致性，同时允许服务提供商以不同方式优化共享日志的写入和读取路径。为了展示共享日志对有状态的无服务器应用的价值，我们构建了 Boki 支持库，实现了容错工作流、持久性对象存储和消息队列。我们的评估显示，共享日志可以将重要的无服务器工作负载加速最多 4.7 倍

## 简介

无服务器计算已经成为了构建弹性云应用已经越来越受欢迎。它的“函数即应用”范式的强大作用，赋能领域包括视频处理，机器学习，分布式编译、事务性工作流和交互式微服务等等。当前无服务器范式中的一个关键挑战，即无服务器函数的无状态特性与构建在其上的有状态应用之间存在不匹配。无服务器应用通常由多个函数组成，其中应用状态是共享的。然而，使用当前的选项（如云数据库或对象存储）管理共享状态往往难以在保持高性能和可伸缩性的同时实现强一致性和容错性。

共享日志（shared log）作为构建存储系统的一种流行方法，它能够同时实现可伸缩性、强一致性和容错性。共享日志提供了一个简单的抽象：一个完全有序的日志，可以同时访问和追加。虽然简单，但共享日志可以有效地支持状态机复制，这是一种已经被深入理解的构建容错有状态服务的方法。共享日志 API 也使得分布式应用摆脱了管理容错共识细节的负担，因为共识协议被隐藏在 API 后面。向无服务器函数提供共享日志可以解决一致性和容错性的双重挑战。

我们介绍了 Boki（日语中意为bookkeeping），这是一个将共享日志 API 导出给函数以存储共享状态的 FaaS 运行时。Boki 使用 LogBook 抽象实现了共享日志 API，其中每个函数调用都与一个 LogBook 相关联。对于 Boki 应用程序来说，它的函数共享一个 LogBook，使它们能够共享和协调对状态的更新。在 Boki 中，LogBooks 让有状态的无服务器应用程序能够以持久性、一致性和容错性管理其状态.

共享日志 API 使用简单，适用于各种应用场景，因此 Boki 面临的挑战是在符合无服务器环境的同时实现高性能和强一致性。数据本地性(locality)是无服务器存储的一个挑战，因为在无服务器环境中，强烈倾向于使用分散式存储。Boki 将读写路径分开，对于读取使用函数节点上的缓存来优化，而对于写入这用扩展带宽(scale-out)来优化写入。Boki 在提供一致性读取和容错性的同时，将写入分散到不同数量的分片上。在 Boki 中，通过一个基于日志的机制，即 metalog，实现了高性能、读取一致性和容错性。

Metalog 定义了 Boki 内部状态的总序，应用程序在需要时可以利用它保证一致性。例如，通过跟踪 metalog 位置来实施单调读取。Metalog 包含元数据，完全有序地排列日志的数据记录。由于 Boki 使用紧凑格式的 metalog，因此一致性和共识至关重要，但高数据吞吐量并不重要。因此，Boki 使用简单的主导式设计(primary-driven,系统的主要操作或控制由一个主要节点或实体来驱动或执行, 而其他节点则根据主要节点的状态进行相应的操作)来存储和更新 metalog。

Boki 通过重新配置来处理机器故障，类似于以前的共享日志系统。由于 metalog 控制着 Boki 的内部状态转换，因此，封闭 metalog（使其不再可写）会暂停状态转换。因此，Boki 通过封闭 metalog、更改系统配置并启动新的 metalog 来实现重新配置。

Boki 的 metalog 允许轻松采用先前共享日志设计中的最新技术的原因。这是因为 metalog 将日志排序、一致性和容错性转变为独立的模块。具体来说，Boki 从 Scalog 中采用了排序技术，从 Delos 的封闭协议中采用了容错技术。另一个好处是它将读取一致性与数据放置解耦，使得可以将日志记录的索引和缓存与函数放置在一起。这意味着在不干扰读取一致性的情况下，云服务提供商可以构建简单的缓存，当将函数调度到数据可能被缓存的节点时，增加数据的本地性。

我们在 Nightcore 上实现了 Boki 的共享日志设计，Nightcore 是一个专为微服务优化的 FaaS 运行时环境，没有针对状态管理的专门机制，而 Boki 则提供了这个功能。Nightcore 的 I/O 效率设计对 Boki 也有利。通过 Nightcore，Boki 在单个 LogBook 上实现了每秒 120 万次的追加吞吐量，同时保持了 p99 延迟为 6.4 毫秒。并且，通过将 LogBook 引擎与函数放置在一起，Boki 实现了最佳情况下 LogBook 读取的延迟为 121 微秒，为了使编写 Boki 应用程序更加简便，我们在 LogBook API 的基础上构建了支持库，针对三种不同的无服务器使用场景：容错工作流、持久对象存储和无服务器消息队列。Boki 支持库利用了来自 Beldi、Tango 和 vCorfu 的技术，同时将它们适应到了 LogBook API 上。Boki 及其支持库在 GitHub 上是开源的。

本论文的主要贡献如下：

- Boki 是一个 FaaS 运行时环境，为有状态的无服务器应用提供了 LogBook API，使其能够以持久性、一致性和容错性管理状态。
- Boki 提出了一个统一的机制，即 metalog，用于处理日志排序、读取一致性和容错性。metalog 解耦了 LogBooks 的读写路径，使得 Boki 能够实现高吞吐量和低延迟。
- 我们构建了 Boki 支持库，利用 LogBook API 来展示共享日志对有状态无服务器应用的价值。这些库实现了容错工作流（BokiFlow）、持久对象存储（BokiStore）和无服务器消息队列（BokiQueue）。
- 我们的评估结果显示：BokiFlow 执行工作流比 Beldi 快 4.3–4.7 倍；BokiStore 的吞吐量比 MongoDB 高出 1.18–1.25 倍，同时执行事务的速度快 1.5–2.3 倍；BokiQueue 的吞吐量比 Amazon SQS 高出 2.14 倍，延迟最高可降低 15 倍。

## 背景和动机

Faas让开发者可以将简单的函数上传到云服务提供商，然后按需调用这些函数。云服务提供商负责管理无服务器函数的执行环境。然而，在当前的 FaaS 范式中，状态管理仍然是一个主要的挑战。由于无服务器函数的无状态特性，当前的无服务器应用程序依赖于云存储服务（例如，Amazon S3 和 DynamoDB）来管理它们的状态。然而，当前的云存储服务无法同时提供低延迟、低成本和高吞吐量。依赖云存储也会增加有状态工作流中的数据一致性问题，因为工作流中的函数可能会在中途失败，导致数据库中存储的工作流状态不一致



#### 共享日志的方法为有状态的无服务器函数提供支持

在当前的 FaaS 范式中，有状态的应用程序往往难以实现其关键状态的容错性和强一致性。举例来说，考虑一个使用无服务器函数构建的旅行预订应用程序。该应用程序有一个用于预订酒店的函数，另一个用于预订航班。在处理旅行预订请求时，会同时调用这两个函数，但两个函数在执行过程中都可能失败，导致状态不一致。使用当前的状态管理方法，例如云对象存储或甚至云数据库，很难确保在失败模型下保持预订状态的一致性。

基于日志的方法在数据一致性和容错性方面取得的成功，促使了在有状态的 FaaS 中采用共享日志。例如，Olive 提出了一个与云存储交互的客户端库，在面对故障时使用预写式redo(write-ahead redo)日志来实现一次性语义。Beldi 则扩展了 Olive 的基于日志的技术，用于事务型无服务器工作流(transactional serverless workflows)。状态机复制(State machine replication, SMR)是另一种通用的容错方法，其中应用状态通过命令日志在服务器之间复制。传统上，命令日志由共识算法支持。但是最近的研究表明，共享日志可以提供有效的抽象来支持基于状态机复制的数据结构和协议。Boki 为无服务器函数提供了共享日志，使得 Boki 的应用程序可以利用这些基于日志的机制高效实现数据一致性和容错性。

通过分析无服务器计算的需求，我们确定了共享日志提供解决方案的三个重要案例。Boki 为这些用例提供了支持库。

- 容错工作流(Fault-tolerant workflows)

- 可持久化对象存储(Durable object storage)

- 无服务器消息队列(Serverless message queues.)

  当前 FaaS 范式的一个限制是函数无法通过传统方法（例如网络套接字）直接通信。共享日志可以自然地用于构建消息队列，提供函数之间的间接通信和协调。我们构建了一个队列库，为无服务器函数提供共享队列。



```
Motivation: serverless functions
  Serverless computing is convenient for developers
    Provider runs function; developer doesn't have to provision machines
  But some challenges:
    State lives in cloud storage
      each function invocation must fetch it
      Boki supports local state between function invocations through its LogBook API
    Provider reexecutes a serverless function that crashed
      ok, if function is idempotent
      With Boki's LogBookAPI, can make function workflows exactly once
```

> 在哪些情况下将用户代码部署在Boki上是有意义的，而在哪些情况下不是呢？

答：那些具有状态的Lambda函数。纯粹功能性的Lambda函数（例如，调整图像大小）从Boki对状态计算的支持中获益不大。具有状态的Lambda函数可以从Boki中受益，因为Boki在函数调用之间保持本地状态。Boki函数可以通过LogBook API来操作该状态

> 在序列号（第3节）中，他们说序列号是单调递增的，但不能保证连续。何时不连续呢？

因为不同的日志簿被合并到一个共享日志中，返回的序列号是记录在共享日志中的位置。

> 共享日志与Raft中的操作日志有什么区别？

共享日志是一个应用级别的抽象。应用程序可以使用共享日志，类似于Raft日志，来实现复制状态机。共享日志也可以被应用程序用于实现其他抽象（例如，精确一次持久函数、队列、键/值存储）；参见Boki库的描述。

共享日志本身必须以容错方式实现；Boki实现依赖于Zookeeper和主从复制，但也可以使用Raft

>  Nightcore对Boki提供了什么？Boki能否建立在另一个FaaS运行时上？

原则上是可以的。Boki需要一个运行时来运行函数，这就是Nightcore提供的。然而，Nightcore可以以较低的成本调用函数；图11(c)中的调用结果如果没有Nighcore可能不会那么好。Nightcore还提供了快速的通信，这也对性能结果产生了积极影响。
