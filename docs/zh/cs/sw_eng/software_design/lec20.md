# Lec 20 项目展示（Project Fair）

2025 年 12 月 10 日，本学期最后一次课，没有配套的课件 PDF——这一讲就是**期末项目展示**（*Project Fair*）本身：全班以类似科技展会的形式，把各自团队做的完整应用摆出来，向同学、助教、嘉宾现场演示、答疑，是整门课程从"问题框架"到"可运行产品"这条主线的收官仪式。

由于总览文件不再单独列出每个作业/项目阶段的清单，这里把整个学期后半段的**期末项目（Final Project）完整时间线**整理在这一讲，方便和前面各讲学到的方法论对照查阅。信息来源：[Final Project 官方页面](https://61040-fa25.github.io/assignments/final-project-main)。

## 期末项目总览

期末项目是团队合作项目，要求每位组员在问题框架、设计、编码等每个阶段都实质参与（可以给每个环节指定一位主要负责人，但不能有人完全不参与某个阶段）。

技术栈要求：必须使用 TypeScript、Deno/Node、MongoDB、Vue.js，以及课程提供的概念服务器与 Sync 引擎；允许在此基础上补充 CSS 框架、文件服务、地图 API 等外部服务，但不能替代核心技术栈。鼓励使用 LLM 辅助编码（课程推荐 `gemini-2.5-pro`），但不建议在后端使用 agentic 编码工具，前端则相对宽松（但可能影响某些评分项）。仓库结构上，前后端各建一个 GitHub 仓库，各自有一位组员做 owner、其余组员做 collaborator；所有非代码类文档统一放在后端仓库里；建议按 feature branch 开发、通过 Pull Request 合并到 main，并采用类似"敏捷冲刺"的增量开发方式，而不是瀑布式的一次性交付。

## 时间线与各阶段要求

| 阶段 | 截止日期 | 交付物 | 呼应的课程内容 |
| :--- | :--- | :--- | :--- |
| Team Contract（团队契约） | 11 月 7 日 23:59 | 约半页的书面协议：每位组员的目标投入度、个人学习/职业目标、开会频率与形式、代码审查等质量保证流程、任务分配与误期处理方式、决策与冲突解决机制 | 团队协作的"操作规程"，避免协作问题拖到项目中期才爆发 |
| Project Updates（导师例会） | 每周（按约定时间） | 每次会议一个文件夹：议程、进度对照开发计划、自上次会议以来的设计变更、问题清单、下周计划；全员必须参加，团队主导讨论、导师作为顾问 | 把"增量开发、持续沟通"落到实处，避免瀑布式开发 |
| Problem Framing（问题框架） | 11 月 12 日中午 12:00（因假期调整） | 领域描述、问题概述、问题真实存在的证据、对标产品分析、功能头脑风暴（比个人项目阶段更长的列表）、伦理分析（含利益相关者分析） | 直接对应 [Lec 1](./lec1.md) 的真实需求识别方法，以及 [Lec 18](./lec18.md) 的价值敏感设计四标准 |
| Project Pitch（项目路演视频） | 11 月 16 日 23:59；11 月 17 日课上展示 | 不超过 3 分钟的视频，形式不限（旁白配幻灯片、采访、白板讨论等），聚焦问题的重要性与方案可行性 | 用简洁的故事说服他人"这个问题值得解决"——呼应 Lec 1 里"真实需求 vs. 创造需求"的判断标准 |
| Functional Design（功能设计） | 11 月 18 日 23:59 | 修订版问题框架、概念规格与 Sync 方案（含非显而易见决策的说明）、单一利益相关者视角的用户旅程叙事、低保真 UI 草图与标注、两页带标注的视觉设计研究、设计总结（说明概念如何整合、如何呼应伦理分析）、含功能分期表/责任分工/风险与应对的开发计划 | 集中呼应 [Lec 2](./lec2.md)/[Lec 3](./lec3.md) 的概念设计四要素、[Lec 4](./lec4.md)/[Lec 5](./lec5.md) 的模块化标准、[Lec 7](./lec7.md) 的用户旅程与线框图、[Lec 14](./lec14.md) 的视觉设计研究 |
| Peer Critique（同侪评审） | 11 月 21 日 23:59 | 每位组员对被分配到的另一个团队项目写一份不超过半页的评审，按"I like / I wish / I wonder"三段式给出建设性反馈，评审对象是路演视频、问题框架与功能设计 | 直接使用 [Lec 14](./lec14.md) 提到的设计批评框架 |
| Checkpoint: Alpha | 11 月 25 日 23:59 | 前后端代码（附 commit hash）、已部署应用的公开 URL、不超过 2 分钟的带语音演示录屏、开发计划进度说明 | 核心功能的最小可用版本（MVP），验收"是否真的能跑起来" |
| Checkpoint: Beta | 12 月 2 日 23:59 | 同 Alpha 的交付物形式，但应用应接近完成，为后续用户测试和打磨留出时间 | 承接 Alpha，为 User Testing 阶段做准备 |
| User Testing（用户测试） | 12 月 7 日 23:59 | 任务列表（含说明与理由）、每位受测用户的测试报告与经验总结、识别出的关键缺陷与改进机会 | 直接对应 [Lec 17](./lec17.md)：基于任务观察用户、而非询问意见，产出是设计修订而非报告本身 |
| Full Demo（完整演示视频） | 12 月 9 日 23:59 | 不超过 3 分钟的视频，语音讲解问题背景，配合应用实际操作的录屏；用真实感数据预先填充应用，模拟"已经被广泛使用"的状态 | 项目成果的最终展示形式 |
| Project Report（项目报告） | 12 月 9 日 23:59 | 全部源代码与设计文档、概念规格与 Sync 方案、导师例会记录、说明变更之处的设计总结、每位组员单独撰写的反思小节 | 对整个项目周期的复盘，呼应 [Lec 19](./lec19.md) 提倡的"把课程思想放回更大背景里理解"的收尾视角 |
| Project Fair | 12 月 10 日 | 现场展示与演示 | 本讲——整门课程的收官 |

**通用要求**：所有非代码类交付物一律使用 Markdown 格式（图表/截图以链接形式插入）；每次截止日期原则上只需要一个团队统一提交（除非特别注明按组员单独提交，如 Peer Critique）；评分默认基于 main 分支上的内容；官方明确表示**不接受迟交**，"以确保项目按计划推进"。

## 从学期主线看期末项目

把这张表和前面二十讲对照，可以看到期末项目本质上是把整门课教的方法论，按真实的产品开发时间线重新走一遍：先用 Lec 1 的问题框架方法找到真实需求，再用 Lec 2–5 的概念设计与模块化标准把需求拆解成可复用的概念积木，用 Lec 6–10 学到的 AI 功能设计与实现技巧把概念变成代码，用 Lec 11、16 的 Sync 与后端知识把概念拼装成完整系统，用 Lec 12–14 的前端与视觉设计把它做成可用的界面，最后用 Lec 17 的用户测试和 Lec 18 的价值敏感设计收尾——检验这个系统是否真的对用户、对社会产生了预期中的正向价值。
