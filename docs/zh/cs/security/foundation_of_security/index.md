# Lec 2 身份认证

如何在计算机系统中验证人员身份？ 身份验证（Authentication）是大多数安全讨论的起点，但实际上也是个问题。

这种场景归结为：**如何处理请求？**  用户请求计算机执行操作，典型的流程为： 认证（Authenticate）——确定请求由哪位用户发出（结果是获得用户标识符）和 授权（Authorize）——判断该用户是否有权执行操作（结果为 Yes/No）。通常来说将认证和授权分离更有益。

最简单场景：人与计算机间的消息交换。 用户 <~~~> 计算机，通过共享秘钥（密码、PIN 码）进行认证。

> 什么是好的密码？或者说好的密码标准是什么？

Solution: 攻击者无法以受害用户身份登录。关键因素：密码的熵值（相对于攻击者对密码分布的认知）。一个事实是，实际密码分布极度倾斜，前 5000 个常用密码可覆盖 20%的账户（数百万个）；不同网站存在相似模式。若密码可预测，即使外观复杂也并非强密码。

其次，密码需限制尝试次数， 即使强密码熵值也有限，计算机可轻松进行百万至十亿次尝试。

最后考虑权衡问题， 系统生成密码熵高但难记忆；用户自选密码墒值不明；强制定期改密可能降低熵值但用户疲于记忆新密码，需权衡不同攻击场景的优先级。□

一个结论是： **通过互联网密码认证难以安全实现**。任意网络节点均可尝试登录，难以强限制尝试次数（同时抗 DoS 攻击）。密码更适用于本地设备认证（如手机 PIN 码），网络认证应优先其他方案。

## 如何存储密码？

稻草人方案：直接存储用户密码表。
风险：若系统被攻破，攻击者获知所有密码，导致：

1. 需重置所有用户密码；
2. 若用户多系统共用密码，攻击者可横向入侵。

改进方案： 哈希存储。  存储用户名和 Hash(password)，认证时计算哈希并匹配。
优点：

- 单项哈希防止直接获取密码，攻击者需要暴力猜测
- 推荐使用慢哈希函数，如 PBKDF2、bcrypt、scrypt
- 与计算哈希表（彩虹表）攻击仍然存在

更优方案： 加盐哈希（salt hash）。 存储用户名、盐值、Hash(盐值 || 密码)。每次创建或更新账户生成新盐，认证时提取盐值计算。有效防御彩虹表攻击（盐值过多无法预计算）。

## 如何通过网络认证？

开放网络中密码认证天然地困难，可借助本地计算机增强安全性。这样的设置： $用户<-->计算机<-->服务器$， 假设计算机可信（虽然存在键盘记录器等风险），更好的方案是： 在客户端存储长密码（如密码管理器），用户先登录本地设备，再使用长秘钥认证服务器；
优点是：服务器认证需高熵密钥；用户记忆密码仅用于本地登录（攻击者需物理窃取设备或植入恶意软件）。

**若用户-服务器链路被监听**，直接发送密码会被窃取。替代方案： **挑战-响应协议（challenge-response protocol）**。

1. 服务器发送随机数（**nonce**）给客户端；
2. 客户端返回 MAC（KDF(密码),  nonce）， 其中 MAC 是后续会讲到的加密哈希；KFD 是慢哈希
3. 服务器验证响应（需存储原始密码）

注意事项：

- 防止客户端误认证错误服务器（应在哈希输入中包含服务器名）；
- 使用慢哈希（KDF）防暴力破解；
- 更高级的方案（如 SRP）可细条哈希存储与挑战-响应。

**若攻击者篡改请求？**需将认证与请求绑定。假设安全通道（如直连线路）不现实，网络中存在窃听和篡改。后面会讲如何建立安全通道。替代方案：将请求直接关联认证（如发送**MAC(KDF(密码), nonce || 请求)**）

**密码另一重大缺陷：易受钓鱼攻击**， 用户可能误向伪装网站（如仿冒银行）泄露密码。

## 本讲小结

- 三种人类认证基础方式：
  - **所知**：密码
  - **所有**：设备
  - **所是**：生物特征
- 不同场景适用不同方法；
- 认证与请求绑定至关重要（后续将讲解 MAC 和安全通道）；
- 密码学广泛用于用户认证；
- 注册建立信任，恢复机制不可或缺；
- 元策略：双因子认证、会话机制、委托登录。

# Lec 4 消息认证码（*MAC*）

到目前为止，我们已经讨论了人员身份验证和文件身份验证。在本节中，我们将探讨通信身份验证。如果两个通信方通过网络进行交流，我们需要通过某种方式确保各方收到的信息确实来自对方，且未在传输过程中遭到篡改。

乍看之下，这似乎不可能实现。如果存在窃听者 Bob 在通信双方之间进行监听，他完全可以替换原始信息并伪造新信息，而接收方将无法察觉。为实现通信验证，我们需要稍作调整并增加一个前提条件——假设通信双方共享某个密钥 k。

在拥有共享密钥 k 的前提下，我们的目标是在信息中添加用于验证真实性的"标签"。这个标签必须基于共享密钥 k 生成函数关系。若非如此，窃听者将能够自行计算有效标签——因为在这个场景中，密钥 k 是 Bob 唯一未知的信息要素。

# Lec 6 数字签名: RSA

在上一节中，我们的认证策略依赖于通信双方共享一个密钥。在那段讨论中，我们完全忽略了这些双方应如何交换该密钥的问题。我们的隐含意思是他们去某个私密房间秘密交换了密钥，但在许多情况下这并不实际：如果他们能低声交换密钥，为何不直接低声交换消息？

幸运的是，利用公钥密码学，可以找到绕过这一共享密钥需求的方法。1976 年怀特菲尔德·迪菲（Whitfield Diffie）和马丁·赫尔曼（Martin E. Hellman）发表的开创性论文《密码学新方向》，首次提出公钥密码学概念，非常值得一读。

## 定义

公钥密码学应用于认证的基本思想是：各方生成两个关联密钥——一个私有签名密钥（secret signing key）和一个公开验证密钥（public verification key）。验证密钥足以验证签名有效性，但无法生成新签名。

# Lec 7 案例研究：公钥基础设施（PKI）

AI 生成；

一次典型的 HTTPS 连接（以 TLS 1.3 为例）过程清晰地展示了这两者是如何结合的：

第 1 步：认证（Authentication） - “握手”与“验明正身”

这是整个连接建立的第一步，也是最关键的一步。

1. **客户端打招呼**：你的浏览器（客户端）连接到网站（服务器），说：“你好，我想建立安全连接。”
2. **服务器出示“身份证”**：服务器会发送它的**数字证书**。这个证书就像网站的“营业执照”，里面包含了：
   - 网站的公钥（Public Key）
   - 网站的身份信息（如域名 `www.example.com`）
   - 由**证书颁发机构（CA）** 用其私钥对以上信息进行的**数字签名**。
3. **客户端验证“身份证”**：你的浏览器内置了信任的 CA 机构的公钥（根证书）。它会做两件事：
   - **验证签名**：用 CA 的公钥去验证服务器证书上的签名是否有效。如果有效，证明这个证书是受信任的 CA 颁发的，不是伪造的。
   - **核对域名**：检查证书里的域名是否和你正在访问的域名一致。
4. **目的达成**：至此，**认证完成**。你的浏览器确认了：“嗯，我现在连接的就是真正的 `www.example.com`，而不是一个钓鱼网站。并且我拿到了它合法的公钥。”

第 2 步：加密（Encryption） - “生成会话密钥”与“秘密通信”

在确认对方身份后，双方开始协商如何加密后续的通信。

1. **生成会话密钥**：你的浏览器会生成一个随机的**对称会话密钥**（比如一个 AES 密钥）。因为对称加密速度远快于公钥加密，适合加密大量数据。
2. **安全传递密钥**：你的浏览器用刚才**验证过的服务器公钥**去**加密**这个随机的会话密钥，然后发送给服务器。
   - 由于只有真正的服务器拥有对应的私钥，因此只有它能解密出这个会话密钥。
3. **开始加密通信**：现在，客户端和服务器都拥有了**相同的会话密钥**。接下来所有的 HTTP 请求和响应数据，都会用这个密钥进行**对称加密和解密**。

这是经典的握手流程，如上图上半部分所示，其设计相对保守，步骤清晰但耗时较长：

1. **Client Hello (客户端打招呼)**
   - 客户端向服务器发送：支持的 TLS 版本、支持的密码套件列表（如`TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384`）、一个客户端随机数（`Client Random`）。
2. **Server Hello (服务器回应)**
   - 服务器回应：选择的 TLS 版本、选择的密码套件、一个服务器随机数（`Server Random`）。
   - **Server Certificate**：发送服务器的数字证书链，用于身份认证。
   - **Server Key Exchange**：（可选）根据选择的密钥交换算法（如 ECDHE）发送服务器的临时公钥参数。
   - **Server Hello Done**：告诉客户端我的部分发完了。
3. **Client Key Exchange (客户端密钥交换)**
   - 客户端验证服务器证书。
   - 生成一个**预主密钥（Pre-Master Secret）**，并用服务器证书中的公钥加密后发送（对于 RSA 密钥交换），或根据服务器参数计算并发送客户端的临时公钥参数（对于 ECDHE 交换）。
   - **Change Cipher Spec**：通知服务器，“接下来我要使用协商好的密钥加密通信了”。
   - **Finished**：发送一条加密后的摘要信息，供服务器验证握手过程是否被篡改。
4. **Server Final Response (服务器最终响应)**
   - 服务器解密出预主密钥（或计算共享密钥）。
   - 客户端和服务器双方利用`Client Random`、`Server Random`和`Pre-Master Secret`独立计算出相同的**主密钥（Master Secret）**，并由此衍生出会话加密密钥。
   - **Change Cipher Spec**：通知客户端，“我也切换好了，接下来用加密通信”。
   - **Finished**：发送一条加密后的摘要信息，供客户端验证。

> [!IMPORTANT]
>
> TLS1.3 握手只需要 1 次往返，极速高效，是现代互联网速度和安全的基石。而 TLS 1.2 需要 4 次
>
> 挥手 2 次往返，确保连接安全关闭。
